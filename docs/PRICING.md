## 1. 무료 / Plus 경계

원칙 세 가지를 먼저 제안합니다.

1. **초대받은 사람은 요금제 때문에 막히지 않는다.** 한도는 그룹을 "만들고 운영하는 사람"(그룹장)에게 걸고, 참여하는 사람에게는 걸지 않습니다. 북극성 지표(주간 확정된 그룹 일정 수)는 초대 → 가입 → 확정 흐름에서 나오기 때문입니다.
2. **이미 무료로 준 기능은 빼앗지 않는다.** 필수 참석자(AVL-010), 그룹 색상 수정(GRP-010), 반복 일정 끝나는 날(CAL-016)은 이미 모두에게 열려 있습니다. 이걸 Plus로 옮기면 기존 사용자에게 "갑자기 잠긴" 경험이 됩니다.
3. **아직 없는 기능으로 Plus를 채운다.** 외부 캘린더 동기화(EXT-001), 개인별 가능 시간대(AVL-012), 큰 그룹·많은 그룹이 Plus의 중심입니다.

## 2. 한도에 닿을 때의 동작

선택지는 **막기**(요청 실패), **경고만**(성공 + 안내), **유예**(일정 기간·인원까지 성공 후 막기) 세 가지입니다.

| 지점 | 누가 겪나 | 제안 | 선택지 |
|---|---|---|---|
| 그룹 만들기 `POST /api/groups` (`web/app/groups/new/page.tsx`) | 그룹장이 될 사람 | **막기**: 4번째 그룹장 그룹은 만들지 않고 업그레이드 안내 | 막기 / 경고만 |
| 초대 미리보기 `GET /api/public/invites/{token}` | 초대받은 사람 | **아무것도 안 함**. 한도 이야기를 꺼내지 않음 | - |
| 초대 참여 `POST /api/groups/join/{token}` — 참여자 쪽 | 초대받은 사람 | **절대 막지 않음**. 참여한 그룹은 참여자 한도에 안 셈 | - |
| 초대 참여 — 그룹 인원 쪽 | 그룹장 / 초대받은 사람 | **유예**: 11~15번째 참여는 성공시키고 그룹장에게만 알림. 16번째부터 참여 실패, 참여자에게는 "그룹이 가득 찼어요. 그룹장에게 알렸어요"만 보이고 그룹장에게 알림 | A. 유예 +5명(제안) / B. 경고만, 막지 않음 / C. 10명에서 막기 |
| 함께 되는 시간 검색 `AvailabilityController` | 그룹 멤버 누구나 | **막지 않음**. 인원이 넘은 그룹도 검색·확정은 됨. 기간은 무료 2개월(지금과 같음) | - |
| 일정 확정·공유 | 그룹 멤버 | **막지 않음** (북극성 지표 그 자체) | - |
| Plus 해지·만료 후 | 그룹장 | 그룹·멤버·일정은 그대로. 새 그룹 만들기와 한도 초과 그룹의 새 참여만 무료 규칙 적용 | - |
| 한도 도입 전에 이미 넘은 그룹·사용자 | 기존 사용자 | **그대로 둠**(삭제·강퇴 없음). 해지 후와 같은 규칙 | 그대로 둠 / 기한 두고 안내 |

원칙: **참여하는 순간에 실패하는 사람은 계정을 갓 만든 사람일 가능성이 높습니다.** 그래서 그룹 인원 한도는 "참여 실패"보다 "그룹장 알림"을 먼저 쓰고, 막는 건 유예를 다 쓴 다음입니다. 막을 때도 실패 응답을 받은 사람이 할 일이 없으니, 그룹장에게 알림을 보내는 쪽이 일을 하게 합니다.

API 오류 모양 제안: 한도 실패는 `403`과 함께 본문에 `code: "PLAN_LIMIT_GROUPS"` 또는 `"PLAN_LIMIT_MEMBERS"`를 실어, `web/lib/api.ts`의 `ApiError`에 `code`를 더해 화면이 업그레이드 안내를 고를 수 있게 합니다(`402`는 브라우저·프록시 처리가 들쭉날쭉해 피합니다).

## 3. 업그레이드 권유 지점과 문구 초안

권유는 **그룹장에게, 한도에 실제로 닿았거나 곧 닿을 때만** 합니다. 초대 화면·로그인 화면·일반 멤버에게는 보이지 않습니다. 같은 안내는 닫으면 7일 동안 다시 띄우지 않습니다.

| # | 화면 (파일) | 언제 | 문구 초안 | 버튼 |
|---|---|---|---|---|

### 단위: 사용자 단위 (제안)

1절 제안에서 한도는 모두 **그룹장의 요금제**로 정해집니다(그룹장 그룹 수, 그 그룹의 인원). 그래서 요금제 상태는 사용자에 두고, 그룹의 한도는 `Group.owner`의 요금제에서 계산합니다. 그룹장을 양도(`POST /api/groups/{id}/transfer/{userId}`)하면 한도도 새 그룹장 기준이 됩니다. 팀/동아리 플랜이 생기면 그때 그룹 단위 표를 더합니다.

### 선택지

| | A. `users`에 컬럼 추가 | B. `subscriptions` 표 따로 (제안) |
|---|---|---|
| 모양 | `users.plan varchar(16) not null default 'FREE'`, `users.plan_expires_at timestamp` | 아래 표 |
| 장점 | 마이그레이션·코드가 가장 작음 | 결제사 ID·상태·이력을 담을 곳이 있음. 웹 결제와 스토어 결제가 같이 와도 행으로 구분 |
| 단점 | 결제사 웹훅 정보(구독 ID, 상태)를 담을 곳이 없어 결국 표를 또 만듦 | 조회 시 조인 한 번 |
| 기존 행 | 기본값으로 모두 FREE | 행이 없으면 FREE라 채울 것 없음 |

B안 `V4__subscriptions.sql` 초안:

```sql
-- 요금제 구독 상태 (#109). 사용자당 여러 행(결제 경로별·이력)일 수 있고, 지금 유효한 행이 없으면 무료다.
create table subscriptions (
    id bigint generated by default as identity,
    user_id bigint not null,
    plan varchar(16) not null,            -- PLUS (이후 TEAM)
    status varchar(16) not null,          -- ACTIVE, CANCELED(기간 끝까지 유효), EXPIRED
    provider varchar(16) not null,        -- WEB_PG, APP_STORE, PLAY_STORE, MANUAL
    provider_ref varchar(255),            -- 결제사 구독/빌링키 ID. 카드번호 등 결제 정보는 저장하지 않는다
    current_period_end timestamp(6) with time zone not null,
    created_at timestamp(6) with time zone not null,
    updated_at timestamp(6) with time zone not null,
    constraint subscriptions_pkey primary key (id),
    constraint uk_subscriptions_provider_ref unique (provider, provider_ref),
    constraint fk_subscriptions_user foreign key (user_id) references users (id)
);

create index idx_subscriptions_user on subscriptions (user_id);
```

- 유효한 요금제 = `status in (ACTIVE, CANCELED)`이고 `current_period_end > now`인 행이 있으면 PLUS, 아니면 FREE. 이 계산은 `PlanService` 한 곳에 둡니다.
- 한도 숫자(3, 10, 유예 5, Plus 상한)는 `WeeklyMetricsService`의 상수를 옮겨 한 곳(`PlanLimits`)에서 측정과 강제가 같이 씁니다.
- `MANUAL`은 결제 연동 전에 고은님이 지인·베타 사용자에게 Plus를 손으로 주는 용도입니다.
- 회원 탈퇴(`AccountService`) 때 이 표 행도 지워야 하므로 탈퇴 경로를 같이 고칩니다. 결제사 쪽 구독 해지도 함께 필요합니다.
- 마이그레이션 영향: 새 표만 만들고 기존 표는 건드리지 않습니다. 기존 데이터 채우기 없음. 운영 PostgreSQL·테스트 H2 모두에서 도는 문법만 씁니다.

## 5. 결제 경로 비교

수수료·조건은 2026-11 기준 공개 자료로 정리한 대략값이며, 계약 전에 고은님이 각 사 최신 약관으로 확인해야 합니다.

| 경로 | 수수료(대략) | 장점 | 단점·준비물 |
|---|---|---|---|
| 국내 PG 정기결제 (토스페이먼츠 빌링, 또는 포트원으로 여러 PG 연결) | 카드 3%대 + 부가세 | 국내 카드·간편결제, 원화, 대학생에게 익숙한 결제창 | 사업자등록·통신판매업 신고, PG 심사, 환불·해지 처리를 직접 구현 |
| Stripe | 국제 카드 약 3~4% | 문서·웹훅·구독 관리가 가장 잘 돼 있음 | 한국 사업자로 직접 가입이 제한적. 국내 간편결제 약함 |
| Merchant of Record (Paddle, Lemon Squeezy 등) | 약 5% + 건당 수수료 | 세금·환불·영수증을 대신 처리 | 수수료 높음, 원화·국내 간편결제 약함 |
| RevenueCat | 월 매출 일정액까지 무료, 이후 매출의 약 1% (결제 수수료와 별도) | iOS·Android·웹 구독 상태를 한 곳에서. 스토어 앱 낼 때 큰 도움 | 결제 자체는 하지 않음(스토어 또는 Stripe 등과 연결 필요). 웹만 있는 지금은 이점이 작음 |
| 스토어 인앱결제 (App Store / Google Play) | 15%(소규모 사업자·구독) ~ 30% | 앱 안 결제가 매끄러움 | 스토어 앱이 아직 없음(전략: 웹 먼저). 앱 안에서 웹 결제로 보내는 것은 정책상 제한됨 |

### 제안: 첫 검증은 웹 결제 하나로

- 지금 사용자는 모두 웹(`app.toogeduler.com`)으로 옵니다. 스토어 앱이 나오기 전이라 스토어 수수료를 낼 이유가 없고, 전략 문서 3단계 설명("웹 결제로 먼저 시작하면 스토어 수수료 없이 검증")과도 맞습니다.
- 국내 대학생 대상이라 **국내 PG 정기결제**(토스페이먼츠 직접 또는 포트원 경유)를 권합니다. Stripe는 한국 사업자 가입 제약 때문에 첫 경로로는 권하지 않습니다.
- RevenueCat은 스토어 앱을 낼 때(4단계) 도입을 다시 봅니다. 4절 `subscriptions.provider`가 경로별로 행을 나누므로 나중에 붙여도 표를 바꾸지 않습니다.
- 스토어 앱 안에서는 구매 버튼을 숨깁니다(3절). 앱에서 산 Plus는 인앱결제를 붙일 때 따로 다룹니다.

사람(고은님)이 준비할 것: 사업자등록·통신판매업 신고, PG 계약·심사, 이용약관(`web/app/terms/page.tsx`)과 개인정보처리방침(`web/app/privacy/page.tsx`)에 유료 서비스·환불·결제 정보 처리 항목 추가.
